# 快速验证方法

## 验证速度优先原则

原型的价值与速度成正比。一个2小时的原型学到的东西可能比2天的原型更多——因为你更快地得到了反馈，更快地修正了方向。

**时间预算参考**：
| 问题复杂度 | 原型时间 | 说明 |
|-----------|---------|------|
| 简单（一个API调用对不对） | 15-30分钟 | 写几行脚本 |
| 中等（状态机设计验证） | 1-2小时 | 小型交互程序 |
| 复杂（架构方案对比） | 半天-1天 | 多个变体实现 |

超过1天还没结论？要么问题定义不清，要么已经在做MVP了。

## 快速验证技术

### 1. Console-First
先用console.log/print验证核心逻辑，不要一开始就搭UI。
```
# 先验证逻辑
python -c "from my_module import process; print(process(test_input))"

# 逻辑对了再考虑界面
```

### 2. Hardcoded Data
用硬编码数据跳过数据获取的复杂性。
```python
# 不要：连数据库获取数据
users = db.query("SELECT * FROM users WHERE active = true")

# 要：硬编码测试数据
users = [{"id": 1, "name": "Alice"}, {"id": 2, "name": "Bob"}]
```

### 3. Single Happy Path
先只验证正常路径，异常处理后面再加。
```
# 原型阶段：只验证主流程
input → process → output ✓

# 不需要：错误处理、边界条件、并发
```

### 4. Manual Verification
不需要自动化断言，人工观察输出即可。
```
# 原型验证方式
运行 → 看输出 → 判断对不对 → 记录结论

# 不需要：
assert result == expected  # 这是测试，不是原型
```

### 5. Quick Visualization
用最快的方式可视化结果。
| 数据类型 | 最快可视化方式 |
|---------|-------------|
| 数字/状态 | print到终端 |
| 列表/表格 | 终端表格或CSV导出 |
| 关系/结构 | ASCII图或Graphviz |
| UI/布局 | 单个HTML文件 |
| 时序/流程 | 终端日志+时间戳 |

## 验证检查清单

原型完成后，回答以下问题：

- [ ] 原型回答了最初的问题吗？
- [ ] 结论是否记录在持久化的地方（commit/ADR/NOTES.md）？
- [ ] 原型代码是否标记为可丢弃？
- [ ] 是否有下一步决策？（合并到真实代码 / 丢弃 / 需要更多验证）

## 常见陷阱

### ❌ 原型变MVP
**信号**：开始写测试、加错误处理、考虑性能
**修复**：停下来。问自己"我要回答的问题是什么？"如果问题已回答，删除原型。

### ❌ 过度设计原型
**信号**：花了30分钟搭项目脚手架
**修复**：单文件能解决的就用单文件。

### ❌ 忘记记录结论
**信号**：原型跑完了，觉得"我记住了"
**修复**：立即写下来。未来的你会忘记。

### ❌ 原型范围蔓延
**信号**：从"验证状态机"变成"验证状态机+UI+持久化+权限"
**修复**：回到一个问题。其他问题开新原型。
